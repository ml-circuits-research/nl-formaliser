3. Logica Z3 & Axiome SMT-LIB2

Toată decizia globală a sistemului este formulată ca o problemă Weighted Partial MaxSMT în SMT-LIB2 (assert pentru legile hard ale schemei w.request + assert-soft ... :weight W pentru preferințele lingvistice și de cost).

3.1 Tipuri Algebrice (smt/prelude.smt2)

Fiecare enumerare din sop-knowledge-worlds/docs/worlds/w.request/schema.sop este reprezentată nativ ca un Algebraic Datatype în Z3, eliminând din start valorile ilegale:

  • Act (19 constructori: ACT_MAKE, ACT_CHANGE, ACT_PLACE, ACT_REMOVE, ACT_ASK, ACT_CONNECT, ACT_GROUP, ACT_TAKE_APART, ACT_PICK, ACT_COPY, ACT_UNDO, ACT_REDO, ACT_SAVE, ACT_LOAD, ACT_SEND, ACT_DESELECT, ACT_GREET, ACT_THANK, ACT_FAREWELL)
  • ActMode (9 constructori: MODE_NONE, MODE_ARRANGE, MODE_MERGE, MODE_UNGROUP, MODE_SPLIT, MODE_DISCONNECT, MODE_REVERSE, MODE_SET, MODE_REPEAT)
  • Mood (MOOD_DO, MOOD_ASK, MOOD_CHECK, MOOD_PROPOSE)
  • Question (20 tipuri: Q_NONE, Q_COUNT, Q_EXISTS, Q_LIST, Q_WHAT, Q_WHICH, ...)
  • TargetMode (TM_NEW, TM_EXISTING, TM_BOUND), TargetFill (6), Det (6), Phase (PH_RESULT, PH_SELECTOR), Want (W_YES, W_NO, W_NOT_ALL).

3.2 Legile Hard (smt/axioms.smt2 + src/smt/encode.mjs)

Nicio soluție nu poate încălca aceste axiome — acesta este motivul pentru care validitatea check.mjs este 100,0% pe toate cele 2.800+ propoziții testate:

; Legea Necesității Lookup-ului (check.mjs):
; Orice țintă existentă neidentificată de cuvinte și care nu e fill=all MUST emite lookup!
(define-fun lookup-law ((tm TargetMode) (tf TargetFill) (identified Bool) (lk Bool)) Bool
  (=> (and (not (= tm TM_NEW)) (not (= tf TF_ALL)) (not identified)) lk)
)

; Coerența Act -> TargetMode:
; act=make creează întotdeauna o țintă nouă; change/remove/place/ask operează pe existentă/bound.
(define-fun valid-act-target-mode ((a Act) (tm TargetMode)) Bool
  (and
    (=> (= a ACT_MAKE) (= tm TM_NEW))
    (=> (or (= a ACT_CHANGE) (= a ACT_REMOVE) (= a ACT_PLACE) (= a ACT_ASK) ...)
        (not (= tm TM_NEW)))
  )
)

; Legea fazei pe ținte noi: pe TM_NEW, constrângerile non-ancoră sunt PH_RESULT.
(define-fun phase-new-law ((tm TargetMode) (is_anchor Bool) (ph Phase)) Bool
  (=> (and (= tm TM_NEW) (not is_anchor)) (= ph PH_RESULT))
)
Invariant Hard în Z3 Ce garantează
Acoperire & Non-suprapunere Fiecare token de conținut este acoperit de cel puțin un candidat (((_ at-most 1) ...) pe fiecare poziție de token previne suprapunerile).
Separare strictă multi-request Pentru cereri active r și r+1: (< rend_r rstart_{r+1}) — elimină 100% defectele de tip gold_hull_overlap.
Puritatea filler-elor Orice FILLER care conține cuvinte de conținut (ex. "That would help", "I appreciate it") este constrâns hard cu span-outside-req, iar emitter-ul scoate exact words=... pe cerere.
Circuite pure-filler (0 cereri) active_1 este opțional doar când toți tokenii de conținut pot fi acoperiți de FILLER (ex. "thanks, that works" → doar @f1, 0 cereri).
Legarea KEY_WORD & asked Orice KEY_WORD selectat trebuie folosit de o constrângere compatibilă (dist ≤ 5, fără a traversa ; sau .), de asked_r (întrebare) sau ca name_words (called/labelled).
Legea verbelor de păstrare (keep/leave) Când act=remove vine dintr-un verb de păstrare și există un selector, cel puțin un selector trebuie să aibă want=no.
Compatibilitate de familie Orice constrângere fam.attr selectată în cererea r forțează fam_r să fie compatibilă cu fam.
Disciplina fragmentelor fără verb Când ppos_r = -1, sunt permise doar make, change, place, ask cu mode=none.
Non-duplicare Două constrângeri identice (același atribut, valoare, operator, fază, polarity) nu pot fi selectate simultan în aceeași cerere.

3.3 Obiectivul MaxSMT (Ponderi Soft)

Când mai multe interpretări sunt formal valide, Z3 maximizează scorul global combinând:

  • Costul candidatului (-cost): potriviri exacte multi-cuvânt (1..2) < valori închise / verbe (2..4) < open-spans (10 + 4*(len-1)) < UNREAD (120).
  • Dezambiguizarea determinerului & rezultativului:
    • a/an → TM_NEW (+18); the/this/my → not TM_NEW (+18);
    • construcția rezultativă make <target> <post-target prop> fără articol nehotărât → act=change, mode=existing (+22) — separă exact "make a blue house" de "make the house blue" și "make boat 67 pixels wide"!
  • Acoperirea cue-urilor gramaticale semantic active: întrebări WH (+45), pronume obiect după verb (make it bold, +24), negații (not/without, +24), cuantificatori universali (all/every, +18).
  • Alinierea act–constrângere: place (+10) pe constrângeri spațiale fără determiner nehotărât; change (+10) pe atribute; *.direction preferat peste *.at sub act=place fără prepoziție statică ("move the boat left" vs "on the left").
  • Economia cererilor și separatori puternici: penalizare -28 per cerere suplimentară, compensată de penalizare -45 dacă o singură cerere traversează un separator puternic (then, afterwards, .) cu verbe pe ambele părți.
  • Legarea key_words & adiacență: bonus +14 pentru constrângeri cu key_words legat și +10 la distanță 1.

3.4 Optimizări de performanță (Elidare de variabile)

Fără elidare, o propoziție de 15 tokeni producea >300 variabile Z3 și 400–4000 ms latență. encode.mjs aplică 4 reduceri exacte (fără nicio pierdere de expresivitate):

  1. Nu creează variabile sel_c pentru tokeni GRAMMAR simpli sau UNREAD multi-token (contopirea UNREAD adiacent se face determinist în emitter).
  2. Elidează ph_c când faza este fixă, wnt_c când nu există niciun NEG în fereastra 1..4 din stânga, și kw_c când nu există niciun KEY_WORD compatibil.
  3. Restrânge domeniul lui asked_r strict la {-1} ∪ attrIds pentru care există efectiv un KEY_WORD în propoziție.
  4. Calculează o margine superioară strânsă R ≤ 4 pe numărul de sloturi de cereri din numărul real de separatori și predicate.

Rezultat: latență mediană ~131 ms și p95 ~783 ms în Z3 WASM (cu segmentatorul Z3 în 2 etape src/smt/segment.mjs).

3.5 Evaluatorul Semantic MaxSMT în Z3 (eval/z3-equiv.mjs)

Pe lângă formalizare, Z3 este folosit și ca judecător semantic conform LEGEND.md v1.2 (--z3-eval): codifică o problemă de aliniere bipartită injectivă map_g ∈ {-1 .. |P|-1} între cererile Gold și Pred, unificând conversiile de unități (1 hour ≡ 60 minutes), clasele de echivalență din k.values și k.objects.stand_in (dinghy ≡ boat), reprezentările canonice (target.name ↔ *.name, target.count ↔ *.count), alternativele defensibile fără stare live (place ↔ make, make ↔ change) și rafinarea validă peste Gold cu unread / cuvinte neacoperite, păstrând însă interdicția strictă pe acțiuni opuse (remove ≠ make → L1a) și valori contradictorii (L1c).
